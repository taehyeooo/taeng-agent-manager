# taeng-agent-manager

> **서비스 아이디어를 말하면, 매니저 에이전트가 기획 → 레포 생성 → 개발 분배 → 테스트·리뷰 → 결과 보고까지 관리하는 멀티 에이전트 시스템**

Orca에서 이 레포를 열고 Claude Code나 Codex 세션을 시작하면, 그 세션이 **매니저**가 됩니다.
매니저는 직접 코드를 짜지 않습니다. 계획을 세우고, 작업을 Claude Code·Codex 워커에게 나눠 주고, 결과를 검증하고, 중요한 결정만 사용자에게 묻습니다.

---

## 한눈에 보기

```
  사용자 ── "할 일 앱 만들어줘" ──▶  매니저 (이 레포를 연 Claude Code / Codex 세션)
                                       │
           ┌───────────────────────────┼───────────────────────────────┐
           ▼                           ▼                               ▼
     ① 기획                       ② 레포 생성                     ③ 개발 분배
   intaeng /기획                 [승인] gh repo create            am task add
   요구사항·정책 확정 [승인]       intaeng 지식베이스 설치          (기본 Codex, 11/30까지)
           │                           │                               │
           └───────────────────────────┴───────────────┬───────────────┘
                                                       ▼
                                    ④ Orca 워커가 각자 워크트리에서 구현·테스트·PR
                                       (Codex / Claude Code, 서로 다른 폴더)
                                                       ▼
                                    ⑤ 교차 검증 — 구현한 모델과 다른 모델이 리뷰
                                       테스트 · reviewflow 4관점 · 보안
                                                       ▼
                                    ⑥ [승인] main 병합 → am report 결과 보고
```

`[승인]` 표시가 있는 단계만 사용자에게 묻고, 나머지는 알아서 진행합니다.

## 빠른 시작

```bash
# 1. 이 기기에서 처음 한 번
python -m am doctor          # git·gh·orca·claude·codex 설치와 로그인 확인
python -m am setup           # 실행 전 권한 검사(가드)가 이 레포를 찾도록 위치 기록

# 2. 다른 노트북에서 이어서 할 때
python -m am restore         # 없는 프로젝트 레포를 보여 줌 (--apply로 clone + Orca 등록)

# 3. 평소
python -m am list            # 모든 프로젝트와 단계
python -m am status <slug>   # 한 프로젝트의 상태와 "다음에 할 일"
```

그다음 매니저 세션에 원하는 서비스를 말하면 됩니다. 매니저가 따르는 규칙은 [AGENTS.md](AGENTS.md)에 있습니다.

## 레포 구조

```
taeng-agent-manager/
├── README.md               ← 지금 보는 문서
├── AGENTS.md               ← 매니저 규칙 (Claude Code·Codex 공통) — 역할, 단계, 승인 정책, 보고 형식
├── CLAUDE.md               ← Claude Code용: AGENTS.md를 불러오고 Claude 전용 스킬만 덧붙임
│
├── am/                     ← 매니저 CLI (Python 표준 라이브러리만, 설치 불필요)
│   ├── cli.py              │  명령어 정의 (python -m am …)
│   ├── state.py            │  프로젝트 상태 · 단계 · 승인 · 작업 · 교차 검증 · 에이전트 배정
│   ├── guard.py            │  실행 전 권한 검사 — 위험한 명령을 실행 직전에 막음
│   ├── report.py           │  결과 보고서 만들기
│   └── doctor.py           │  도구 설치·로그인 확인 (Codex 워커가 구현)
│
├── projects/               ← 프로젝트별 상태 (git으로 공유 → 다른 노트북에서도 그대로)
│   └── <slug>/
│       ├── project.json    │  단계, 레포, 승인 기록, 작업 목록, 검증 결과, 이력
│       └── docs/           │  레포를 만들기 전의 기획 문서 (spec·plan)
│
├── config/
│   └── agents.json         ← 작업 배정 선호 (지금: Codex 우선, 디자인 포함, 2026-11-30까지)
│
├── docs/
│   └── architecture.md     ← 설계 문서 — 재사용 vs 새로 만든 것, 상태 모델, 가드 동작, 한계
│
├── scripts/
│   └── check_approvals.py  ← CI: 기존 승인 기록이 바뀌거나 지워지면 실패
│
├── tests/                  ← 단위 테스트 (python -m unittest discover -s tests)
│
├── .claude/settings.json   ← 가드 훅 연결 (도구 실행 전에 am/guard.py 호출)
├── .github/workflows/      ← CI: 테스트 (Ubuntu·Windows) + 승인 기록 검사
└── .am/                    ← 이 기기 전용 경로 (git에 올라가지 않음)
```

각 서비스 프로젝트는 **이 레포 밖의 별도 GitHub 레포**로 만들어지고, 작업마다 별도 워크트리(작업 폴더)에서 개발됩니다.

## 역할

| 계층 | 누가 | 하는 일 |
|---|---|---|
| **매니저** | 이 레포를 연 세션 | 계획, 작업 나누기, 에이전트 고르기, 검증 결과 모으기, 승인 요청, 보고 |
| **코디네이터** | Orca | 워크트리 만들기, 워커 실행, 완료 보고·질문 전달 |
| **작업 에이전트** | Codex · Claude Code | 설계, 구현, 버그 수정, 테스트 — 자기 워크트리에서 PR까지 |
| **검증 에이전트** | 구현한 쪽과 **다른 모델** | 코드 리뷰, 테스트, 보안 검사 (고치지 않고 지적만) |

역할은 고정하지 않습니다. 지금은 사용자 요청에 따라 **Codex가 기본**이고(디자인 포함, 11/30까지), 12/1부터 자동으로 Claude로 넘어갑니다.

## 승인 정책

| 구분 | 내용 |
|---|---|
| ✅ **알아서 진행** | 코드 읽기·분석, 승인된 범위 안 수정, 워크트리에서 개발, 테스트·린트·빌드, 리뷰·오류 수정, 로컬 커밋 |
| ✋ **사용자 승인** | GitHub 레포 생성·공개 설정, 원격 push, main 병합, 배포, 파괴적 삭제, 운영 DB 변경, 인증정보 접근, 시스템 설정 변경, 유료 서비스, 주요 구조·정책 변경 |
| ⛔ **금지** | 승인 우회 옵션, 인증정보 노출, 관련 없는 프로젝트 수정, 상태 파일 직접 수정, 검증 생략 |

승인 요청은 개발 용어 없이 **무엇을 / 왜 / 승인하면 / 안 하면 / 되돌릴 수 있나 / 추천** 형식으로 한 번에 하나씩 묻습니다.

### 어떻게 지키나 — 세 겹

1. **실행 전 검사 (`am/guard.py`)** — 에이전트가 명령을 실행하기 직전에 훅이 검사합니다. 승인이 기록되지 않은 위험 작업은 실행하지 않고 승인 요청으로 바꿉니다. 에이전트가 스스로 승인을 기록할 수는 없습니다.
2. **에이전트 자체 안전장치** — Orca 권한을 "대신 승인"으로 두면 Codex는 읽기 전용 칸막이 + 인터넷 제한 상태로 돌고, 그 밖의 일은 AI 자동 검토를 거칩니다. 무조건 막는 벽이 아니라 위험도를 판단하는 검토입니다.
3. **GitHub 서버 보호** — main은 PR과 자동 검사를 통과해야만 바뀝니다. (승인 후 적용 예정)

가드는 안전벨트일 뿐 완벽한 차단 장치가 아닙니다. 막을 수 없는 부분(파일로 된 스크립트의 내용 등)은 [docs/architecture.md](docs/architecture.md) 5장에 적어 두었고, 그래서 2·3번 겹을 함께 둡니다.

## 주요 명령

| 명령 | 하는 일 |
|---|---|
| `am new <slug> --idea "…"` | 새 서비스 아이디어 등록 (기획 단계로 시작) |
| `am status <slug>` | 상태와 다음 할 일 |
| `am task add <slug> "<제목>" [--kind design]` | 작업 추가 — 에이전트를 안 고르면 선호 설정대로 자동 배정 |
| `am task verify <slug> <id> --by <검증자> …` | 검증 결과 기록 (테스트·리뷰·보안 모두 통과해야 다음 단계) |
| `am approve <slug> <항목>` | 사용자 승인 기록 — 사용자 확인 없이는 실행되지 않음 |
| `am report <slug>` | 결과 보고: 수행 에이전트, 변경 파일, 검증 결과, 미해결, 자동 진행한 일, 승인 필요한 일 |
| `am restore` | 다른 노트북에서 프로젝트 레포 복원 |

전체 목록은 `python -m am --help`.

## 기존 플러그인 재사용

새로 만든 것은 **여러 프로젝트에 걸친 상태 관리**와 **실행 전 권한 검사**뿐이고, 나머지는 [taeng-marketplace](https://github.com/taehyeooo/taeng-marketplace) 플러그인과 Orca를 그대로 씁니다.

| 필요한 것 | 담당 |
|---|---|
| 아이디어 → 기능명세서·구현 순서 | intaeng `/기획` |
| 프로젝트 레포 규칙·지식베이스·커밋 훅·CI | intaeng `/지식베이스` |
| 디자인 (구조 시안 → 세부 시안 → 적용 → 고도화) | intaeng `/디자인` — Claude·Codex 모두 설치됨 |
| 워커에게 줄 작업 지시문 | intaeng `/맡기기` |
| PR 마무리 · 순서대로 병합 · 이어하기 | intaeng `/마무리` `/머지` `/이어하기` |
| 코드 리뷰 (정확성·테스트·보안·규칙 + 검증) | reviewflow |
| API 스모크 테스트 | qaflow |
| 워커 실행 · 워크트리 격리 · 완료 보고 | Orca orchestration |
