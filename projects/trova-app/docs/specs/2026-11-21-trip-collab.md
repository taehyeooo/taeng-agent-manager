# 여행 같이 고치기 (공유 링크로 친구와 함께 편집) — 기획서

작성 2026-11-21 · 상태: 사용자 확정(2026-11-21 "진행해") · 대상: trova-backend + trova-app

## 배경
- 지금 공유는 "보기 + 내 여행에 담기(복사)"까지다(앱 PR #175, `POST /api/public/trips/{token}/copy`). 복사본은 각자 따로 고친다.
- 사용자 요청(2026-11-21): "친구끼리 공유할 때 공유 받은 사람이 로그인해서 자기 앱에도 들어와 있는지랑 서로 수정할 수 있게 하는 거".
- 비슷한 앱(Google Docs·Notion·Figma·여행 계획 앱)은 실시간 공동 편집이 기본이다.

## 확정한 정책 (사용자 답, 2026-11-21)
| 항목 | 결정 |
|---|---|
| 친구 권한 | **만든 사람과 똑같이** — 장소 추가·삭제·순서·시간·메모, AI 다시 짜기·말로 바꾸기·대안 장소 모두 가능. 단 **여행 삭제, 멤버 내보내기, 링크 끄기/새로 만들기는 만든 사람만** |
| 반영 속도 | **실시간** — 우리 서버의 SSE(서버→앱 소식 보내기)로, 외부 유료 서비스 없음(0원). 앱이 백그라운드에서 돌아올 때·연결이 끊겼다 이어질 때 한 번 새로 받기 |
| 링크 방식 | **링크 하나에 선택** — 같은 공유 링크를 연 사람이 "내 여행에 담기(복사)" 또는 "같이 고치기 참여" 중 고른다 |
| 안전장치(매니저 제안, 함께 확정) | 만든 사람이 멤버 목록 보기·내보내기, 링크 끄기/새로 만들기(이전 링크 무효 — 이미 참여한 멤버는 유지), 멤버 상한 10명 |

## 사용자 흐름
1. 만든 사람: 여행 상세 → 공유 → 링크 보내기(지금과 같음). 공유 시트에 "이 링크로 친구가 같이 고칠 수 있어요" 안내와 멤버 목록·링크 관리.
2. 받은 사람: 링크 열기 → 일정 미리보기(로그인 없이 지금처럼) → 버튼 두 개: **"같이 고치기 참여"**(주) / "내 여행에 담기(복사)"(보조). 로그인 안 했으면 로그인 후 고른 동작을 이어서 한다(지금 담기의 로그인 이어가기 방식 재사용).
3. 참여하면 그 여행이 받은 사람의 '내 여행'에 **같은 여행**으로 나타난다(카드에 "함께" 표시·멤버 얼굴/이름 첫 글자).
4. 누가 고치면 열어 둔 다른 멤버 화면에 바로 반영되고, 바뀐 곳을 잠깐 표시("민수가 경포호를 추가했어요" 토스트). 앱을 안 보고 있던 멤버에게는 푸시 알림(묶어서, 과하지 않게 — 같은 사람의 연속 변경은 5분 안에 한 번).
5. 멤버는 "여행에서 나가기" 가능. 만든 사람은 멤버 내보내기 가능.

## 서버 (trova-backend, Spring Boot + PostgreSQL)
- **멤버 표** `trip_members(trip_id, user_id, role[OWNER|EDITOR], joined_at)` — 기존 여행 소유자는 마이그레이션으로 OWNER 행 생성.
- **권한 검사 교체**: 여행·장소·일정·AI(다시 짜기·대화·대안)·공유 API의 "소유자인가"를 "멤버인가"로. OWNER 전용: 여행 삭제, 멤버 내보내기, 공유 링크 끄기/재발급. 한곳(권한 서비스)에서 판단하고 컨트롤러는 그걸 부른다.
- **참여 API** `POST /api/public/trips/{token}/join` — 로그인 필요, 링크 유효·멤버 상한(10)·이미 멤버면 그대로 성공. 응답 tripId.
- **멤버 API** `GET /api/trips/{id}/members`, `DELETE /api/trips/{id}/members/{userId}`(OWNER, 또는 본인=나가기).
- **동시 수정 충돌**: 여행·장소 엔티티에 낙관적 잠금(JPA `@Version`). 충돌 시 409 + 최신 상태 → 앱이 "친구가 방금 바꿨어요. 새로 불러왔어요" 후 다시 적용할 수 있게.
- **실시간**: `GET /api/trips/{id}/events`(SSE, 멤버만). 변경 API가 성공하면 그 여행 구독자에게 `{type, actorName, summary, version}` 소식 전송. 서버 한 대라 메모리 안 구독자 목록으로 시작(나중에 여러 대면 Kafka로 소식 전달 — 이미 의존성 있음). 25초마다 살아 있음 신호, 연결 상한·인증 만료 시 종료. Nginx/프록시 버퍼링 끄기 설정 확인.
- **변경 기록** `trip_activity(trip_id, actor_id, type, summary, created_at)` — 토스트·알림 문구와 디버깅용(최근 100건 유지).
- **푸시**: 기존 Expo 푸시로 "○○가 여행을 고쳤어요" — 같은 사람 연속 변경은 5분 묶음, 알림 끄기는 기존 알림 설정 따름.
- **AI 사용 한도**: 실행한 사람 몫으로 계산(기존 사용자별 한도 그대로).
- 기존 `copy`는 그대로 유지.

## 앱 (trova-app, Expo/React Native + React Query)
- 공유 받은 화면(SharedTripScreen): "같이 고치기 참여"(주)·"내 여행에 담기"(보조) 버튼, 로그인 후 이어가기.
- 내 여행 목록·여행 상세: "함께" 표시, 멤버 줄(이름 첫 글자 원, 최대 4 + n).
- 공유 시트: 멤버 목록·내보내기·나가기, 링크 끄기/새로 만들기(OWNER만), 안내 문구.
- 실시간: 여행 상세가 열려 있을 때만 SSE 연결(react-native-sse 같은 가벼운 라이브러리 또는 fetch 스트림 — 새 네이티브 모듈이 필요하면 스토어 빌드가 필요하므로 **순수 JS 방식 우선**). 소식을 받으면 React Query로 그 여행을 새로 받기 + 토스트. 앱이 앞으로 올 때·재연결 시 한 번 새로 받기.
- 409 충돌 처리: 최신 상태 반영 + 안내, 사용자가 다시 시도.
- 문구는 해요체, 우리 디자인 규칙(주황=실행·초록=도움, 얇은 선 아이콘) 따름.

## 코드 확인 결과로 정한 구현 방식 (2026-11-21)
- 소유자 검사가 서버 13개 파일 약 38곳(TripService 16곳)에 흩어져 있다 → 권한 서비스 하나로 모으는 것이 필수, 검증 때 흩어진 검사 잔존 여부를 따로 확인.
- 변경 소식은 기존 패턴(Spring `publishEvent` + `@TransactionalEventListener` + `@Async` 푸시, PushEventListener)을 그대로 쓴다: `TripChangedEvent`(거래 완료 후).
- **Kafka 사용(사용자 결정 2026-11-21 "카프카 쓰는게 좋지 않아?")**: ADR 0021과 같은 방식 — `TripEventBus` 하나로 모으고 `app.trip-events.type`으로 고름. kafka = 토픽 `trova.trip-events`(Aiven 무료 플랜, 키 = tripId), 서버마다 고유 그룹으로 받아 자기 SSE 구독자에게 전달. 보내기 실패·브로커 꺼짐이면 서버 안 전달로 자동 넘기기(지표 남김). 비용 0원.
- Caddy가 SSE를 바로 흘려보낸다(프록시 버퍼링 설정 거의 불필요 — 배포 때 확인).
- 인증: 앱(네이티브)은 머리글 지원 순수 JS SSE 라이브러리. 웹(PWA) 기본 EventSource는 머리글을 못 붙이므로 60초 1회용 연결 표(`POST /api/trips/{id}/events/ticket` → `?ticket=`)를 쓴다(토큰을 주소에 넣지 않음).
- 충돌 잠금은 여행 단위 버전(일정 수정이 여러 장소를 같이 바꾸므로).
- 비교: WebSocket(양방향 불필요·무거움), 주기적 새로 받기만(실시간 아님), 외부 실시간 서비스(유료·데이터 외부) → SSE 채택.

## 하지 않는 것 (이번 범위 밖)
- 같은 장소를 동시에 글자 단위로 고치는 실시간 문서 편집(Google Docs식 커서 공유) — 장소 단위로 충분.
- 역할 고르기(보기 전용 멤버) — 이번엔 모두 같은 권한.
- 채팅·댓글.

## 수용 기준
1. 링크를 받은 사람이 로그인 후 "같이 고치기 참여"를 누르면 그 여행이 자기 '내 여행'에 같은 여행으로 보인다.
2. A가 장소를 추가·삭제·순서 변경·시간 변경하면, 여행 상세를 열어 둔 B 화면에 3초 안에 반영되고 토스트가 뜬다.
3. A·B가 동시에 같은 장소를 바꾸면 한쪽이 409 안내를 받고 최신 상태로 다시 고칠 수 있다(데이터가 조용히 덮이지 않는다).
4. 멤버가 아닌 사람은 여행·장소·실시간 API에 접근할 수 없다(403). 내보낸 멤버는 즉시 접근이 끊긴다.
5. OWNER만 여행 삭제·멤버 내보내기·링크 끄기/재발급이 된다. 링크를 새로 만들면 이전 링크로는 참여·조회가 안 된다(이미 멤버는 유지).
6. 멤버 10명이 차면 참여가 안 되고 안내가 나온다.
7. 앱이 백그라운드에서 돌아오면 최신 상태로 보인다.
8. 무선 업데이트(OTA)로 내보낼 수 있다 — 새 네이티브 모듈 없이(필요하면 스토어 빌드로 바꾸고 미리 알린다).
9. 추가 비용 0원(외부 유료 서비스 없음).

## 검증
- 백엔드: 권한(멤버/비멤버/OWNER 전용) 단위·통합 테스트, 낙관적 잠금 409 테스트, SSE 구독·전송·권한·끊김 테스트, 마이그레이션(기존 여행 OWNER 생성) 테스트.
- 앱: 참여·담기 흐름, 실시간 반영(두 계정 — 테스트 계정 2개, 로컬/개발 서버), 409 안내, 백그라운드 복귀.
- 교차 검증: 구현 모델의 반대쪽.
