# Trova 백엔드 성능·안정성 계획 (초안, 2026-11-18)

근거: Trova 레포 측정 기록(문제 기록 `docs/monitoring/2026-11-04-capacity-issue-log.md`, r1~r28, ADR 0005·0037·0039·0040·0041·0042·0050, `docs/bench/*`, 작업 기록) + 2026-11-18 QA1(낮은 부하 조회 11분, Grafana 실측).

## 1. 지금 상태 한 줄
서버가 아주 작다(Oracle E2.1.Micro: 실제 CPU 1/8 OCPU 버스트, 메모리 956MiB, safeKor 수집기 동거). 조회 처리량 상한 약 75요청/초(CPU 몫이 한계), 메모리 여유 약 187MiB. 평소 응답은 괜찮지만(오늘 주요 API p95 88~353ms), **영상 분석 + 조회 몰림 + 재시작이 겹치면 메모리·CPU가 바닥나 장애**가 난다(11-08 조회 붕괴, 11-13 9시간 중단·23분 장애).

## 4. 추천 순서
- 1단계(1주, 위험 낮음): A1 → B1·B2 → B3. 성공 기준: 여행 상세 p95 353→200ms 이하, 요청당 DB 쿼리 수 수치화, 404 기록 0, Slack 경보 시험 통과.
- 2단계(2주): C2 → C1(CI 학습), D1. 성공 기준: 재시작 후 UP 시간·첫 10분 p95, RSS 구성표, Google 호출 감소율.
- 3단계(결정 필요): E1 서버 이전 검토(A1 재고 확인·ARM 빌드 시험 → 이전 계획 ADR). D2는 정확도 평가(evalflow)와 함께.
- 측정 규칙(11-13 이후): 운영 부하 측정은 조회 50명까지, 재시작 30분 뒤, 공개 주소로, 시작 전 사용자에게 알림. QA·측정·배포 동시 금지.
